# HomeCloudBackend — Storage Index Manager v1

Индексирование существующих файлов на локальных дисках, NFS и SMB без копирования или изменения содержимого. Применяется **поверх** `storage.scan` и `storage.files.list`.

**Установка:** распаковать ZIP **в корень проекта**, заменив совпадающие файлы. Важно после установки выполнить `go run . init-db`, чтобы появилась новая таблица `hc_storage_index`; затем `go test ./... -count=1` и перезапустить `go run . serve`.

**Управление:** обычный `ws://127.0.0.1:8080/ws`, сначала `hello`, затем команды. Для скачивания используется существующий `/ws/storage`.

**Параметры:** `storage_id` — идентификатор ранее зарегистрированного хранилища. В примерах ниже использован тестовый NFS ID; заменять не нужно, если ID у тебя тот же.

## 1. STORAGE.INDEX — добавить найденные файлы в индекс

```json
{
  "v": 1,
  "id": "index-001",
  "type": "command",
  "action": "storage.index",
  "data": {
    "storage_id": "50fefe420c21a7050550ac1b33c17713",
    "recursive": true,
    "exclude": ["backups/jupyter/**"]
  }
}
```

Немедленный результат: `job_id`, `status: running`. В фоне сервер рекурсивно обходит том и добавляет метаданные в SQLite. **Ничего не переносит, не удаляет и не перезаписывает на диске.**

Директории `.homecloud/**` и `backups/jupyter/**` **всегда** исключаются, даже без `exclude` (в версии v1). Дополнительные исключения принимают относительные пути (например, `backups/private/**` или `*.tmp`). Путь в `exclude` всегда относительно корня зарегистрированного хранилища.

## 2. STORAGE.INDEX.STATUS — узнать ход работы

```json
{
  "v": 1,
  "id": "index-status-001",
  "type": "command",
  "action": "storage.index.status",
  "data": {
    "job_id": "JOB_ID_ИЗ_STORAGE_INDEX"
  }
}
```

Состояния: `running`, `completed`, `partial`, `failed`, `cancelled`. Поля: `files_seen`, `files_indexed`, `bytes_seen`, `errors_count`, `errors`, `complete`, `missing_marked`, `started_at`, `finished_at`.

Дополнительно можно подписаться на два серверных события:

```json
{"v":1,"id":"index-sub1","type":"subscribe","topic":"storage.index.progress"}
```

```json
{"v":1,"id":"index-sub2","type":"subscribe","topic":"storage.index.finished"}
```

Прогресс публикуется с интервалом около 2 секунд; окончательное состояние всегда доступно через `storage.index.status`, даже если клиент пропустил событие.

## 3. STORAGE.REINDEX — повторная синхронизация

```json
{
  "v": 1,
  "id": "reindex-001",
  "type": "command",
  "action": "storage.reindex",
  "data": {
    "storage_id": "50fefe420c21a7050550ac1b33c17713",
    "recursive": true,
    "exclude": ["backups/jupyter/**"]
  }
}
```

Повторный обход **сохраняет `file_id`** неизменённых путей, обновляет размер, тип и дату изменения. Если **весь рекурсивный обход завершился без ошибок**, отсутствующие ранее индексированные файлы помечаются `available: false`, кроме намеренно исключённых. Если NFS отказал в доступе или процесс прерван, пометки об отсутствии **не выполняются** — нельзя принимать частичный результат за полное содержимое диска.

При `recursive: false` файлы из вложенных папок не помечаются отсутствующими.

## 4. STORAGE.FILES.LIST — общий индекс

```json
{
  "v": 1,
  "id": "index-files-001",
  "type": "command",
  "action": "storage.files.list",
  "data": {
    "storage_id": "50fefe420c21a7050550ac1b33c17713",
    "limit": 100
  }
}
```

Ответ содержит **управляемые загрузки** (`source: managed`) и **физические файлы, найденные индексатором** (`source: indexed`, `relative_path`, `available`). Для индексированных файлов SHA-256 изначально пустой — индексатор намеренно не перечитывает терабайты ради хеширования.

`limit` от 1 до 500 (по умолчанию 100). Индекс не заменяет полноценную файловую навигацию или постраничный поиск; это будущие задачи.

## 5. STORAGE.FILES.GET — метаданные по ID

```json
{
  "v": 1,
  "id": "index-file-001",
  "type": "command",
  "action": "storage.files.get",
  "data": {"file_id": "FILE_ID_ИЗ_STORAGE_FILES_LIST"}
}
```

## 6. STORAGE.DOWNLOAD.PREPARE — скачать существующий файл

```json
{
  "v": 1,
  "id": "index-download-001",
  "type": "command",
  "action": "storage.download.prepare",
  "data": {"file_id": "FILE_ID_ИЗ_STORAGE_FILES_LIST"}
}
```

Работает для `managed` **и** `indexed`. Перед выдачей файла сервер проверяет разрешённый корень, действительный путь и отсутствие выхода за пределы хранилища. Размер сверяется с индексом: если файл изменился, выполните `storage.reindex`.

Для `indexed` SHA-256 считается **во время скачивания**, и результат включается в `storage.complete` на `/ws/storage`.

## 7. STORAGE.INDEX.CANCEL — отменить работу

```json
{
  "v": 1,
  "id": "index-cancel-001",
  "type": "command",
  "action": "storage.index.cancel",
  "data": {"job_id": "JOB_ID_ИЗ_STORAGE_INDEX"}
}
```

Отменяется **только задание**, уже индексированные строки не удаляются. Ответ `status: cancelling`; окончательное состояние `cancelled` подтверждается через статус или событие.

## Ограничения v1

- Одновременно не более двух заданий глобально и одного на хранилище.
- До 250 000 файлов и 15 минут на задание; при достижении лимита состояние `failed`, уже сохранённые строки остаются.
- Статусы заданий хранятся в RAM сервера (индекс файлов — в SQLite); после перезапуска статусы теряются.
- Обход не следует за символическими ссылками. Непрочитанные из-за ограничений Windows NFS каталоги отображаются в `errors`; результирующий индекс может быть частичным.
- Новая таблица создаётся только при явном `go run . init-db` или включённой существующей авто-миграции.
- В этой версии доступ к API по-прежнему ограничивается доверенной LAN/Tailscale, а `device_id` **не является аутентификацией**.
- Поскольку внешние файлы могут изменяться независимо от базы, индекс — это снимок, а не гарантия текущего состояния диска.
